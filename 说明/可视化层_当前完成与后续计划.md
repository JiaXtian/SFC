# 可视化层当前完成工作与后续需求计划

## 1. 文档定位

本文档聚焦当前项目中的可视化层，不将其表述为完整运维监控平台。现阶段前端更适合作为“算法结果展示与交互验证界面”，其价值在于：

1. 展示卫星拓扑与部署结果。
2. 展示节点、链路、候选方案和部署明细。
3. 为后续动态编排、故障恢复和策略可解释性展示预留交互入口。

因此，当前可视化层已经具备“原型级演示能力”，但距离“动态星地协同编排监控平台”仍有明显扩展空间。

## 2. 当前已完成工作

### 2.1 已完成三维星座拓扑展示

当前前端已经实现：

1. 三维地球场景与卫星星座展示。
2. 星间链路展示。
3. 不同渲染质量、星空背景、旋转控制等显示配置。

这使得系统已经具备直观展示卫星拓扑结构的能力，可用于演示星座规模、卫星分布和链路连接关系。

### 2.2 已完成节点与链路资源明细展示

当前已经可以在界面中查看：

1. 卫星节点的轨道参数。
2. 节点 CPU / 内存 / 磁盘使用情况。
3. 当前节点承载的 VNF 情况。
4. 节点在业务中的入口/出口角色。
5. 链路的总带宽、可用带宽、时延、可靠性与状态。

这说明前端已经能够承接任务书中“多域资源感知与表征”的部分展示职责，至少在星上节点和链路层面形成了可视表达。

### 2.3 已完成候选方案可视化与部署交互

当前候选方案弹窗已经支持：

1. 展示 `top-k` 候选方案。
2. 展示算法处理耗时。
3. 展示源节点、目的节点。
4. 展示候选是否满足 SLA 约束。
5. 展示时延、带宽、可靠性等违规原因。
6. 展示方案评分和评分拆解。
7. 支持用户确认部署或强制部署。

这部分已经具备较强的“策略可解释性展示”基础，对后续算法汇报和演示很有价值。

### 2.4 已完成部署结果展示与回滚交互

当前部署面板已经支持：

1. 展示部署状态、时延、部署时间。
2. 展示入口/出口节点与 VNF 落点。
3. 展示链路路径与路径总时延。
4. 支持部署高亮。
5. 支持回滚并刷新资源状态。

这意味着前端已经不是单纯的静态展示页面，而是具备了与后端编排执行联动的交互能力。

### 2.5 已具备基础实时更新能力

当前已经接入 WebSocket，用于接收部署状态更新，因此前端具备最基础的实时反馈能力。虽然范围还比较有限，但为后续扩展为动态拓扑和故障态实时监控提供了入口。

## 3. 当前可视化层的局限

### 3.1 重点仍是“静态拓扑 + 结果展示”，不是“动态过程展示”

当前前端最强的是展示某一时刻的拓扑、资源和候选结果，但尚未完整展示：

1. 拓扑随时间的持续变化过程。
2. 业务负载随时间的潮汐变化。
3. 故障发生、影响扩散、恢复和迁移过程。
4. 编排策略在连续时间轴上的决策轨迹。

因此，当前前端更适合支撑静态方案演示，不足以完整表达真实动态星地协同编排过程。

### 3.3 缺少动态故障感知与恢复展示

任务书明确要求重调度、自适应容错和故障恢复。当前界面虽能显示链路状态，但缺少以下关键表达：

1. 节点故障与链路故障事件的实时告警。
2. 故障前后编排路径对比。
3. 重调度触发原因和执行轨迹。
4. 自愈完成时间、受影响业务数、恢复成功率等指标展示。

这部分是后续可视化层最重要的补强方向之一。

## 4. 后续需求计划

### 4.1 从结果展示升级为动态过程可视化

建议将后续重点从“部署结果展示”升级为“动态编排过程展示”，重点补充：

1. 时间轴回放能力。
2. 拓扑快照切换或连续动画。
3. 节点资源、链路带宽、时延、可靠性随时间的变化趋势。
4. 同一业务在部署、迁移、重调度、自愈过程中的状态变化。

这样前端才能真正体现“动态调度决策编排仿真分析”的价值。

### 4.2 增加核心算法可解释性表达

当前候选方案评分展示已经是很好的基础，后续建议继续增强：

1. 显示剪枝前候选规模、剪枝后候选规模。
2. 显示 A2C 策略最终选择节点的原因。
3. 显示嵌入矩阵或关键特征贡献的摘要结果。
4. 显示严格约束方案与放松约束 fallback 方案的差异。

这样不仅能展示结果，还能体现算法智能性与工程合理性。

### 4.3 补齐故障恢复与容错可视化

建议增加以下功能：

1. 节点/链路故障事件面板。
2. 受影响 SFC 列表和影响范围热区。
3. 故障前路径、故障后重路由路径对比。
4. 重调度耗时、恢复成功率、自愈完成时间展示。
5. 强制部署、降级部署、迁移部署等状态标签。

这部分将直接支撑任务书中的“故障恢复和容错处理功能”展示要求。

### 4.4 增加全局指标看板

建议新增全局可视化看板，集中展示：

1. 当前总卫星数、可用卫星数、故障节点数。
2. 链路活跃率、拥塞链路数、平均时延。
3. 已部署业务数、SLA 满足率、失败率。
4. 算法平均处理时延、P95 处理时延。
5. 负载均衡度、资源利用率、迁移次数。

这样可视化层才能从“局部详情查看”升级为“系统运行态势展示”。

### 4.5 增强多域协同表达

尽管当前阶段重点不在完整系统工程，但为与研究目标保持一致，后续可视化层应逐步支持：

1. 星上节点、地面节点、边缘节点的分层显示。
2. 域内和跨域路径的差异化样式。
3. 跨域迁移、跨域调度、跨域故障恢复的状态展示。
4. 星座构型参数与多域资源指标的联合呈现。

这会让界面更符合“星地一体化核心网动态编排体系”的展示目标。

## 5. 面向任务书的可视化落地建议

### 阶段一：补齐动态展示基础能力

1. 引入拓扑时间轴与快照播放。
2. 将 WebSocket 扩展到拓扑变更、故障事件、重调度事件。
3. 在界面上增加资源趋势图与事件流。

### 阶段二：补齐故障与重调度展示

1. 显示节点故障、链路故障和业务中断风险。
2. 增加故障后路径切换动画。
3. 增加恢复结果统计和自愈状态展示。

### 阶段三：补齐多域协同与指标看板

1. 加入星地多域资源图层。
2. 增加统一运行态势看板。
3. 与核心算法层动态 A2C / 剪枝 / 嵌入矩阵更新结果联动显示。

## 6. 建议在汇报中采用的表述

建议将当前可视化层表述为：

“当前已完成面向卫星拓扑与 SFC 编排结果的三维可视化原型，支持节点/链路资源展示、候选方案对比、约束违规原因展示、部署结果展示与回滚交互，并具备基础实时状态更新能力。下一阶段将重点补齐动态拓扑演化、故障感知与恢复过程展示、全局指标看板和星地多域协同可视化能力，以支撑动态编排算法验证与系统方案论证。” 

## 7. 结论

当前可视化层已经能够有效支撑核心算法原型演示和部署结果解释，但后续仍需从“静态结果展示界面”升级为“动态编排过程与故障恢复监控界面”。只有这样，才能与核心算法层的动态化改造形成完整呼应。
