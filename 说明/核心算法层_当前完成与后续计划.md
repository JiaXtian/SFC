# 核心算法层当前完成工作与后续需求计划

## 1. 文档定位

本文档仅聚焦本项目的核心算法层，不将其表述为“完整编排系统已全部实现”。当前代码库的重点成果主要集中在以下三部分：

1. 静态卫星拓扑上的 SFC 部署推理与资源扣减流程已经贯通。
2. 地面训练侧已经具备 `GNN + DRL(A2C) + 启发式剪枝` 的原型链路。
3. 数据生成侧已经能够生成较大规模卫星拓扑和带 SLA 的请求样本，但仍然主要服务于静态或准静态场景。

因此，当前成果更适合被定义为“面向星地一体化核心网智能编排的核心算法验证原型”，而不是面向真实动态星地环境的完整工程系统。

## 2. 当前已完成工作

### 2.1 静态拓扑 SFC 推理主链路已贯通

当前后端已经形成一条可运行的静态推理链路：

1. 生成 Walker-Delta 星座拓扑。
2. 为卫星节点初始化 CPU / 内存 / 磁盘 / 负载 / 节点可靠性。
3. 为星间链路初始化带宽、可用带宽、时延、链路可靠性与状态。
4. 接收 SFC 请求并根据约束生成候选部署方案。
5. 对候选方案进行资源校验、链路最短路径计算、可靠性估计与部署执行。
6. 在部署后扣减节点和链路资源，并支持回滚。

这说明项目已经具备“从资源输入到部署决策输出”的最小可验证闭环。

### 2.2 资源表征体系已具备基础雏形

从当前代码看，已纳入或部分纳入以下指标：

1. 节点资源指标：CPU、内存、磁盘。
2. 节点业务负载指标：`core_network_load`。
3. 链路指标：链路状态、可用带宽、总带宽、时延、链路可靠性。
4. 业务 SLA 指标：最大时延、最小带宽、最小可靠性。
5. 星座构型指标：总卫星数、轨道面数、高度、倾角。

这已经基本覆盖任务书中“至少 5 类指标”的主干要求，但当前仍缺少多域异构资源的统一建模，尤其缺少地面节点、边缘节点、容器实例状态、迁移代价等实体。

### 2.3 已有候选方案生成与约束评估能力

当前推理侧已经做了以下工作：

1. 基于拓扑缓存和 Dijkstra 的最短路计算。
2. 对链路故障状态和零带宽链路进行跳过。
3. 按节点剩余资源、链路带宽、路径时延、可靠性估算生成可行候选。
4. 支持 `top-k` 候选输出。
5. 支持在严格约束不足时进行有限放松，产出 fallback 候选方案。

这意味着当前算法并不是简单随机放置，而是已经具备了“约束驱动候选搜索”的基础能力。

### 2.4 训练侧已具备真实后续方向所需的关键骨架

虽然当前在线后端仍以静态推理为主，但 `train` 目录已经包含后续动态智能编排需要的关键构件：

1. `GNNEncoder`：用于拓扑图表征。
2. `DRLAgent(A2C)`：包含 Actor / Critic 结构。
3. `HeuristicPruner`：用于候选节点剪枝，缩小动作空间。
4. `SFCEnvironment`：把资源、SLA、路径、可靠性纳入训练环境。
5. `onboard_inference`：提供机载推理原型，已经把启发式剪枝和 DRL 决策串联起来。

因此，严格来说，本项目并不是“还没有 A2C / 剪枝方向”，而是“训练和机载原型中已有该方向骨架，但尚未完整接入在线动态编排主系统”。

### 2.5 数据生成已具备大规模样本生成基础

当前 `train/ground_training/data_generation` 已经支持：

1. 生成增强版 Walker-Delta 星座。
2. 生成 800 / 2500 / 6000 等不同规模拓扑。
3. 为节点生成 CPU、内存、磁盘、负载、可靠性指标。
4. 为链路生成状态、带宽、可用带宽、时延、抖动、可靠性。
5. 生成携带 SLA、优先级、负载等级的 SFC 请求样本。

这部分工作已经为后续大规模训练、算法对比和性能评估打下了基础，也为“支持模拟星座卫星数量 >= 4800”提供了可扩展数据基础。

## 3. 当前能力与真实需求之间的核心差距

### 3.1 当前在线算法仍然主要针对静态拓扑

当前已完成的后端主流程，本质上仍然是“单时刻静态拓扑上的一次性部署推理”。它尚未完整覆盖真实需求中的：

1. 动态星座拓扑持续变化。
2. 链路随时间切换、时延抖动和容量波动。
3. 容器迁移与重调度。
4. 节点或链路故障触发后的在线自愈。
5. 星地协同多域联合编排。

这也是后续开发最重要的转向点。

### 3.2 嵌入矩阵生成尚未形成动态时序闭环

当前 GNN 编码器和后端 ONNX 推理已经具备“图嵌入 + 策略选择”的基础，但仍是偏静态单帧输入。真实场景应进一步发展为：

1. 针对连续拓扑快照生成时序嵌入矩阵。
2. 在决策时显式使用历史窗口信息，而不是只看当前时刻。
3. 将链路切换、轨道位移、拥塞演化、故障概率纳入 embedding 更新。

换言之，后续重点不是简单“再调参数”，而是把嵌入矩阵从静态图表示升级为动态时序图表示。

### 3.3 A2C、启发式剪枝与在线推理尚未工程化融合

目前这三个部分在训练侧和机载推理原型里是存在的，但与后端服务化编排还没有完全形成一致闭环，表现为：

1. 后端线上候选搜索与训练时动作空间定义并未完全统一。
2. 剪枝策略和在线约束校验仍存在两套逻辑。
3. 动态拓扑下的 A2C 状态更新、重调度触发和策略切换机制尚未定型。

因此，后续不是从零开始，而是需要完成“算法原型到在线编排服务”的一致化和工程收敛。

### 3.4 数据仍偏“静态样本集合”，而非“动态场景生成器”

当前数据生成器虽然指标比较全，但生成方式仍主要是“独立拓扑文件 + 独立请求文件”。这不等同于真实动态卫星网络场景。真实需求需要的是：

1. 同一星座随时间连续演化的拓扑序列。
2. 同一节点和链路资源在时间轴上的连续变化。
3. 少量低概率故障事件的可控注入。
4. 与调度事件、迁移事件、恢复事件联动的数据回放能力。

这部分是后续算法能力能否可信验证的关键。

## 4. 后续开发重点

### 4.1 核心方向一：从静态部署推理转向动态智能编排

后续核心算法层应优先聚焦以下主线：

1. 将单次静态部署扩展为连续时序决策问题。
2. 在动态拓扑上持续生成节点嵌入矩阵和上下文状态向量。
3. 将 A2C 作为动态编排主策略之一，用于多步部署、迁移和重调度。
4. 保留启发式剪枝作为在线推理加速模块，降低动作空间，确保处理时延向 `<=500ms` 目标逼近。
5. 把故障感知、自愈恢复、迁移代价、负载均衡纳入统一奖励或约束体系。

### 4.2 核心方向二：建立“动态场景 + 在线重调度”算法闭环

建议把后续算法闭环定义为：

1. 动态拓扑感知。
2. 时序图嵌入更新。
3. 启发式候选剪枝。
4. A2C 编排决策。
5. 资源分配执行。
6. 故障触发重调度。
7. 容器迁移与恢复效果评估。

这条闭环比当前“静态候选规划”更符合任务书中星地协同、故障感知、容器迁移、负载均衡和自愈恢复的总体要求。

## 5. 数据生成侧的后续改进计划

这是后续必须补强的重点，不应被视为辅助性工作。

### 5.1 从单快照生成升级为时间序列场景生成

建议新增“动态拓扑序列生成器”，使每个样本不再是单个拓扑，而是：

1. `topology_t0 ... topology_tn`
2. 对应每个时刻的节点资源状态
3. 对应每个时刻的链路可达性、带宽、时延、抖动
4. 对应每个时刻的业务请求流入和已部署实例状态

这样训练和评估才能真实模拟“高动态服务拓扑与资源需求变化”。

### 5.2 提高卫星拓扑演化的物理一致性

当前拓扑已经具备 Walker-Delta 基础，但后续需要增强以下方面：

1. 卫星位置连续变化，而非独立随机重采样。
2. 轨道面、相位、可见性和星间链路建立/断开的时间连续性。
3. 链路状态变化应与轨道几何和距离约束一致。
4. 支持更精确的星座构型参数表征和回放。

目标不是做轨道力学仿真平台，而是保证生成数据足够准确地表征编排算法所依赖的动态拓扑指标。

### 5.3 增强资源与业务负载的联动生成

建议让数据生成从“随机资源值”升级到“受业务驱动的资源演化”：

1. 节点 CPU / 内存 / 磁盘占用随历史部署任务变化。
2. 链路带宽占用随流量变化而动态收缩或恢复。
3. 业务负载等级与请求到达率、链路压力、热点区域相关联。
4. 引入局部热点、潮汐流量和区域性拥塞。

这样才能支撑负载均衡和弹性伸缩相关算法验证。

### 5.4 注入低概率节点/链路故障机制

根据你的要求，后续必须支持“概率极小部分节点或链路故障”。建议采用：

1. 低概率节点失效事件。
2. 低概率链路中断事件。
3. 短时抖动型故障与持续型故障区分。
4. 故障恢复时间、故障影响范围、故障持续时长参数化。
5. 故障前后保持时间连续，便于测试重调度与自愈策略。

注意故障比例应足够低，避免训练样本被大量异常事件主导；建议把故障作为可配置稀疏事件，而不是常态事件。

### 5.5 增加多域星地节点与迁移代价建模

虽然当前阶段重点是核心算法，但为了后续与任务书更一致，数据生成应逐步补充：

1. 地面节点、边缘节点、中心节点等多域资源实体。
2. 容器启动时延、迁移时延、镜像大小、冷启动代价。
3. 跨域带宽、跨域时延、跨域可靠性差异。
4. 星地协同场景下的域间切换成本。

这部分不一定先在可视化层全面呈现，但应尽早进入训练数据与奖励函数设计。

## 6. 面向任务书的后续研发路线建议

### 阶段一：动态数据与算法接口统一

1. 把训练环境、机载推理原型、后端在线推理的状态定义统一。
2. 将动态拓扑序列生成器纳入 `train/ground_training/data_generation`。
3. 统一节点、链路、SLA、故障、迁移相关字段。

### 阶段二：动态编排策略成型

1. 建立时序嵌入矩阵生成机制。
2. 把启发式剪枝和 A2C 策略在动态场景中联调。
3. 引入重调度、迁移、自愈奖励项。
4. 输出处理时延、SLA 满足率、恢复成功率、迁移代价等统计指标。

### 阶段三：服务化接入与性能收敛

1. 将训练得到的策略导出并接入后端在线服务。
2. 增加动态探测周期控制，向 `<=30s` 感知周期靠拢。
3. 优化在线推理耗时，向 `<=500ms` 处理时延靠拢。
4. 在 `>=4800` 星规模下完成压力测试与指标验证。

## 7. 建议在汇报中采用的表述

建议将当前项目成果表述为：

“当前已完成静态卫星拓扑下的 SFC 智能部署推理原型，实现了资源感知、链路约束评估、候选方案生成、部署执行与回滚；训练侧已具备 GNN、A2C 强化学习、启发式剪枝和机载推理原型，为后续动态场景编排奠定了算法基础。下一阶段重点转向动态拓扑时序嵌入、A2C 在线编排、故障感知重调度以及动态精确卫星拓扑与稀疏故障数据生成能力建设。” 

## 8. 结论

当前核心算法层已经完成“静态场景可运行、训练骨架具备、数据基础可扩展”的阶段性工作；后续最关键的工作不是简单补界面，而是把动态拓扑、时序嵌入矩阵、A2C 在线决策、启发式剪枝、故障重调度和高保真动态数据生成，真正收敛为一个统一的动态智能编排算法体系。
